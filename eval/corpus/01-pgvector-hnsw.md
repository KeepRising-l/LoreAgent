# PostgreSQL 16 与 pgvector HNSW 索引原理及参数调优笔记

在搭建面向个人知识库的轻量级 RAG 系统时，一个核心架构决策是：是否引入独立向量数据库（例如 Milvus 或 Qdrant），还是直接在 PostgreSQL 16 中启用 `pgvector` 扩展。对于单机或中小规模知识库（十万到百万级片段）而言，使用 PostgreSQL 16 配合 `pgvector` 可以把业务表（会话、消息、文档元信息、审计轨迹）和向量片段放在同一个事务库里，避免跨系统双写不一致与运维复杂度膨胀。

## 一、为什么选择无固定维度的 `vector` 列类型

pgvector 支持两种列定义方式：固定维度 `vector(1536)` 与无固定维度 `vector`。许多早期教程直接推荐在建表 DDL 中写死 `vector(1536)`，但在工程实践中，这会带来非常明显的升级代价：

1. **多模型维度冲突**：OpenAI `text-embedding-3-small` 默认是 1536 维，本地轻量开源模型（如 `bge-small-zh`）通常是 512 维，而 `bge-m3` 则是 1024 维。如果表字段写成 `vector(1536)`，只要你想切换成 1024 维模型，PostgreSQL 会直接报错拒绝写入，导致新旧模型向量无法在同一张 `chunks` 表中并存过渡。
2. **平滑重建索引**：采用无固定维度 `vector` 列之后，可以额外增加 `embedding_model` 与 `dim` 两列做显式隔离。在切换新 Embedding 模型进行全量重建（Reindex）期间，系统可以先为新模型写入新版本切片，查询侧通过 `where embedding_model = :activeModel` 限定只比较同一向量空间下的片段；等全量重建完成并校验通过后，再原子切换生效模型并删除旧模型切片，整个切换过程几乎零停机。
3. **注意事项**：无固定维度的 `vector` 列不能直接建立跨维度的全局 HNSW 索引；当数据量增大需要建立向量索引时，必须配合按模型隔离的部分索引（Partial Index），例如针对单一模型、固定维度做表达式转换后建索引。在几千到几万条片段的中小规模知识库中，严格按 `user_id`、`active_version`、`tags` 预过滤后的顺序扫描或精确距离计算耗时通常在几毫秒到十几毫秒之间，已足够流畅。

## 二、HNSW 与 IVFFlat 索引的核心差异

在 pgvector 中，最常用的两种近似最近邻（ANN）索引是 **IVFFlat** 与 **HNSW**：

- **IVFFlat（倒排聚类索引）**：建索引前需要表中已有足够数据以训练 K-Means 聚类中心（lists），建索引速度快、内存占用较低；但当后续数据分布发生较大变化或大量新增文档后，如果聚类中心长期不重新训练，召回率会明显下降。此外，如果查询过滤条件过窄导致某些聚类桶为空，召回数量可能不足 Top-K。
- **HNSW（分层可导航小世界图）**：基于多层图结构，上层节点稀疏用于快速大跨度跳转，底层包含全部节点用于精细邻域搜索。HNSW 不依赖预先聚类，随文档增量写入即可动态插图维护，在相同查询延迟下通常拥有更高的 Top-K 召回率。代价是建图耗时较长且图索引占用内存较高（若索引能常驻 PostgreSQL 的 `shared_buffers`，查询 P99 延迟会非常稳定）。

## 三、HNSW 关键参数解析与调优经验

创建 HNSW 索引与查询时有三个决定“构建耗时—内存占用—召回率—延迟”平衡的核心参数：

1. **`m`（每层节点的最大出度，默认 16）**
   - 含义：控制图中每个节点在每一层最多保留多少条邻居边。
   - 影响：增大 `m`（例如调到 24 或 32）能增强图连通性，在向量维度较高（如 1536 维）时显著提升高召回区间的表现；但建索引时间、磁盘体积和内存开销会随 `m` 近似线性增长。个人知识库场景保持 `16` 到 `24` 即可。
2. **`ef_construction`（建索引时的候选队列宽度，默认 64）**
   - 含义：插入新向量寻找近邻连边时，动态维护的候选列表大小。
   - 影响：调高 `ef_construction`（例如 128）不会增加最终索引体积，但会延长建索引耗时，同时提高图边质量，避免局部陷入次优路径。建议 `ef_construction >= 2 * m`。
3. **`ef_search`（查询时的候选队列宽度，默认 40）**
   - 含义：每次执行 `ORDER BY embedding <=> $1 LIMIT k` 时，图搜索阶段维护的动态候选集大小。
   - 影响：这是可以在请求/会话级别动态调节的运行参数（`SET LOCAL hnsw.ef_search = 100`）。当存在较高比例的 `WHERE` 过滤条件（例如按 `tags` 或 `doc_date` 筛选）时，部分图上走到的近邻节点会被过滤掉，此时适度调大 `ef_search` 或使用 pgvector 0.8+ 的迭代扫描特性可以有效避免召回结果数少于预期的问题。

## 四、距离度量算子选择：余弦距离 `<=>` vs 内积 `<#>` vs 欧氏 `<->`

pgvector 提供了三种核心距离操作符：
- `<->`：L2 欧氏距离（`vector_l2_ops`），适合向量未归一化且模长本身有物理意义的场景；
- `<#>`：负内积（`vector_ip_ops`），注意 pgvector 为了配合 `ORDER BY ... ASC` 升序排列索引，返回值是点积的**相反数**；
- `<=>`：余弦距离（`vector_cosine_ops`），等价于 `1 - cosine_similarity`，取值范围 `[0, 2]`（完全同向为 `0`，正交为 `1`，完全反向为 `2`）。

对于文本 Embedding 模型输出的向量，即便部分模型（如 OpenAI、BGE）已做 L2 单位化（此时 L2 距离平方、负内积与余弦距离排序完全等价），在 SQL 与代码可读性上仍强烈推荐统一采用 **`<=>` 余弦距离**，并在 SQL 投影中显式换算为相似度：`1 - (c.embedding <=> cast(? as vector)) AS score`。这样相似度自然落在 `[0, 1]` 区间（反向为负），极易与拒答策略的最低相关性阈值对齐，也方便在调试接口 `/api/retrieval/debug` 中直观排查低分噪声片段。

## 五、预过滤（Pre-filtering）与后过滤（Post-filtering）的陷阱

在带权限与知识库范围的检索中，有一个极其常见却危害很大的实现错误：**后过滤**。所谓后过滤，是指先把 `ORDER BY embedding <=> ? LIMIT 5` 的 Top-5 从向量库捞出来，再在 Java 内存里根据 `user_id` 或 `tags` 把不满足条件的片段删掉。

这种写法会造成两个严重后果：第一是**安全与数据越权风险**，如果排序逻辑稍有疏忽，别人或禁用标签的内容可能进入上下文；第二是**空召回假象**——假设用户指定 `tags = ['java']` 并取 Top-3，而全局最相似的 5 个片段全属于 `['python']`，后过滤会把 5 条全删光返回 0 条，明明知识库里有匹配的 `java` 笔记却被误判为「依据不足」。

因此，正确做法必须坚持 **作用域过滤在检索前完成**：在 PostgreSQL 的同一条查询语句里把 `c.user_id = ?`、`d.user_id = ?`、`c.version = d.active_version` 以及 `d.tags && ?::text[]` 全部写进 `WHERE` 子句，再接 `ORDER BY ... LIMIT ?`。在有索引及事务隔离保障下，所有不合条件的文档在排序截断之前就会被排除在候选集之外，既保证了多租户与标签边界安全，又确保返回的 Top-K 全部来自目标范围内最相关的片段。
